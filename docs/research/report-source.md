# 암행어흥 — 리뷰 신뢰를 제품 경험으로 만드는 설계

대상: 제품 책임자·디자인·개발 팀 · 조사 2026-09-08~09 · 한국어 모바일 서비스

## 결론

암행어흥의 품질 기준은 **소비자가 근거를 보고 선택하고, 업체가 지적에 답하며, 독립된 감찰로 변화를 확인하는 경험**이다. 기존 디자인 문서의 ‘비용을 내는 업체도 결과를 바꾸지 못한다’는 의도를 유지한다. 화해의 참고 가치는 조건별 탐색, 균형 잡힌 리뷰 요약, 설명이 붙은 개인화, 공통 컴포넌트에 있다. 화해 앱의 화면이나 브랜드를 그대로 복제할 필요는 없다.

이번 작업은 저장소 문서와 핵심 소스의 대조, 공식 자료 기반 비교 조사, 전체 화면군의 설계 정리, 디자인 이미지 생성, 홈·검색·공개 감찰 리포트 개선을 포함한다. 별도 외부 원본 기획서는 발견되지 않았으며 모든 기능의 출시 품질을 완성했다고 주장하지 않는다.

## 1. 내부 자료에서 복원한 제품

제품의 명시적 원칙은 app/DESIGN_SYSTEM.md에 있다. 감찰 모집에서는 업체를 가리고, 지적과 개선을 함께 보여주며, 캐릭터는 안내에만 사용하고, 숫자를 지어내지 않는다는 규칙이다. 코드에서는 소비자·감찰관·업체 3역할, Flutter/Riverpod/go_router 프런트와 Express/Supabase 백엔드, 감찰·리뷰·에스크로·교육·구독·추천·담합 방지 기능군을 확인했다.

그러나 문서와 실제 구현은 달랐다. 홈의 정산·등급·알림은 고정값이었고, 소비자 리포트는 업체 전용 /report API를 호출하면서 오류를 빈 0점 데이터로 숨겼다. 자동 게시 서비스는 다음 리뷰에서 언급하지 않은 과거 지적을 fixed로 전환했다. 이는 디자인보다 우선해서 고쳐야 할 정보 신뢰 문제였다. 상세 근거 파일과 화면 목록은 저장소 조사 목록에 정리했다.

## 2. 화해에서 가져올 기준

화해는 개인 조건에 따라 리뷰를 좁히는 필터를 소개했고, 제품 정보 도움말에서는 키워드·사진·정렬을 통한 탐색을 설명했다. 이 자료들은 각각 2019년과 2020년의 기능 설명이므로 현재 앱의 모든 UI가 동일하다는 근거로 사용하지 않았다. 암행어흥에는 실제 수집된 업종·지역·관찰 항목부터 적용하는 것이 타당하다. [화해 개인화 발표](https://blog.hwahae.co.kr/all/newsroom/news/816), [화해 제품 정보 도움말](https://blog.hwahae.co.kr/all/how-to/tip/3476)

2022년 화해의 리뷰 토픽은 상세 상단에서 장점과 아쉬운 점을 함께 보여주고, 개인 조건에 맞게 요약을 좁히도록 설계됐다. 암행어흥에서는 긍정·부정 관찰을 나란히 보여주고 원문으로 연결하는 데 적용했다. 후기 한 줄을 매장의 보편적 사실처럼 확장하지 않는다. [화해 리뷰 토픽 발표](https://blog.hwahae.co.kr/all/newsroom/news/8313)

2026년 궁합 점수는 사용자 프로필·사용 이력·리뷰·성분 데이터를 결합하며 분석 리포트도 제공한다. 이 발표는 개인화가 근거 데이터에 의존한다는 사례다. 암행어흥은 현재 데이터만으로 AI 신뢰도를 만들어내는 대신 조건과 표본을 표시해야 한다. [화해 궁합 점수 발표](https://blog.hwahae.co.kr/all/newsroom/news/15537)

화해의 안드로이드 팀은 공통 디자인 시스템을 통한 일관성과 개발 효율을 설명했다. 암행어흥도 기존 AppCard·AppButton·AppLayout을 재사용하고, 홈과 상세에서 동일한 장단점 카드로 읽기 흐름을 맞췄다. 해당 인터뷰는 회사의 자체 보고이며 사용자 만족도 향상 폭을 입증하는 연구는 아니다. [화해 플랫폼 인터뷰](https://blog.hwahae.co.kr/all/hwahaeteam/people/14418)

## 3. 근거가 보이는 신뢰

방문 자료 확인, 경제적 관계, 리뷰의 평가는 서로 다르다. FTC 플랫폼 지침은 긍정·부정 리뷰를 공정하게 다루고, 의미를 바꾸는 편집을 피하고, 경제적 관계와 수집·집계 방식을 명확히 설명하도록 권고한다. 구매자 확인형 시스템도 허위 리뷰에 면역은 아니다. 이 자료는 미국 지침이며 한국법 준수 결론으로 사용하지 않았다. [FTC 플랫폼 리뷰 지침](https://www.ftc.gov/business-guidance/resources/featuring-online-customer-reviews-guide-platforms)

Google Maps 정책은 대가를 제공받은 리뷰와 이해충돌에 제한을 둔다. 따라서 내부 유료 감찰 리포트를 외부 일반 소비자 리뷰로 자동 게시하는 기능은 별도 정책 검토가 필요하다. 조사 담당자는 공식 본문을 확인했으나 본 담당자의 재열람은 429/접속 차단으로 실패했다. 이 제한을 명시하며 외부 게시 기능은 이번 변경에 추가하지 않았다. [Google Maps 콘텐츠 정책](https://support.google.com/contributionpolicy/answer/7400114?hl=en)

한국 추천·보증 심사지침은 국가법령정보센터 검색에서 새 버전의 존재가 확인됐으나 현행 동적 본문을 충분히 추출하지 못했다. 따라서 표시 문구가 현행 국내법을 충족한다고 결론 내리지 않는다. 다음 출시 검토에서는 실제 지원 주체·범위·시점과 최신 본문을 대조해야 한다. [국가법령정보센터 추천·보증 심사지침](https://www.law.go.kr/행정규칙/추천ㆍ보증등에관한표시ㆍ광고심사지침)

## 4. 사용성은 동작과 상태까지 포함한다

Flutter는 시스템 글자 크기를 존중하면서 큰 글자에 필요한 공간을 확보하도록 안내한다. Android 터치 목표 48dp와 iOS 44pt도 설명한다. 이번 설계는 48 logical px 목표, 자동 높이 카드, 줄바꿈 필터와 최대 본문 폭을 채택했다. [Flutter 접근성 설계](https://docs.flutter.dev/ui/accessibility/ui-design-and-styling)

WCAG 2.2 AA의 최소 타깃 24 CSS px와 확장 기준의 44 CSS px는 서로 다르며, 플랫폼의 48dp 지침과 혼동하지 않아야 한다. 일반 본문 대비 4.5:1, 200% 글자 확대, 상태 메시지 전달을 품질 점검에 반영한다. 이 작업의 위젯 검사는 전체 앱 접근성 인증이 아니다. [W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/)

## 5. 적용한 설계와 코드

- 홈: 가치 설명→검색→업종→안내→최근 감찰→지역별 랭킹. 고정 정산액·등급·알림 점과 근거 없는 ‘인증됨’을 제거했다.
- 데이터: 소비자 홈은 보호된 미션 API를 불필요하게 호출하지 않는다. 섹션별 오류와 정상 빈 목록을 구분하고, 늦은 이전 응답을 폐기한다.
- 검색: 업종 조건 전달, 디바운스, 요청 세대 관리, 지우기 시 타이머 무효화, 오류 재시도, 조건 초기화. 서버 최대 50개 표시를 총 검색 건수로 오해하지 않게 했다.
- 공개 리포트: 공개 API를 사용한다. 지적·약속·기록을 평균보다 위에 배치한다. 평균은 5점 척도와 공개 리뷰 수로 표시하며 누락을 0점으로 바꾸지 않는다.
- 백엔드: 공개 분석에 지적 조회 상태와 이력을 추가하고 리뷰 조회 장애를 성공한 0건처럼 반환하지 않게 했다. 미언급을 개선 완료로 처리하던 자동 해결을 중단했다.
- 과거 데이터: 예전 fixed 기록은 증거 재확인이 필요한 처리 기록으로 표시한다. 운영 DB를 임의로 되돌리지 않았다.

## 6. 디자인 이미지의 역할

생성형 이미지 도구로 홈·검색·리포트 3화면의 콘셉트 보드를 제작했다. 기존 어흥이 캐릭터와 크림·골드·먹색 팔레트를 참고했다. 최초 이미지의 ‘확인 완료’ 카드에 미래 재감찰 문구가 들어간 오류를 발견하고, 해당 문구를 실제 확인을 묘사하는 예시 문장으로 수정했다.

이 이미지는 디자인 예시이며 운영 화면 캡처가 아니다. 업체·사진·숫자는 합성이다. 화면의 실제 동작은 Flutter 코드에 구현했고, 시안의 모든 장식·사진·정렬 기능을 그대로 구현했다고 주장하지 않는다. 최종 이미지와 생성 프롬프트는 design 폴더에 저장했다.

## 7. 남은 제품 결정

가장 중요한 후속 단계는 항목별 재감찰 증거 API와 운영 감사다. 지적 ID·배정 미션·관찰 시각·증빙·판정자·멱등 키를 결합하고 확인 불가 상태도 보존해야 한다. 그 전에는 ‘언급 없음’을 ‘고침’으로 바꾸지 않는다.

또한 업종 ID 정규화, 구독 혜택과 신뢰 배지 분리, 고정 ROI 예측 문구 검토, 유료 감찰 지원 관계 필드, 실제 결제·정산·분쟁 시나리오 검증이 남아 있다. 원본 기획서가 따로 있다면 복원 명세와 대조해야 한다. 화면군별 동선·상태·API·권한·우선순위는 제품 설계 명세에 정리했다.

## 8. 조사 범위와 한계

저장소 문서 목록, 역할·라우트·스키마·상수, 핵심 화면·서비스를 조사했다. 모든 소스 줄에 대한 보안 감사나 전체 운영 DB 검증은 아니다. 화해 최신 로그인 앱을 직접 사용한 사용성 연구도 아니다. 공개된 공식 기능 설명과 개발 자료를 비교 근거로 삼았으며 과거 발표와 2026년 발표를 구분했다.

검색은 화해 공식 서비스·리뷰·랭킹·개인화에서 시작해 리뷰 정책·접근성 원문으로 좁혔다. 두 독립 조사 결과를 합친 뒤 핵심 출처를 재확인했다. 탐색·요약·개인화·데이터 신뢰·접근성의 설계 판단에 근거가 모였고, 추가 일반 검색보다 코드 결함 수정과 화면 검증의 가치가 높아 이 범위에서 수집을 종료했다. 해결되지 않은 국내 지침 본문과 실운영 상태는 제한으로 남겼다.

# 암행어흥 제품 설계 명세

기준일 2026-09-09 · 대상: 제품 책임자, 디자인, Flutter/백엔드 개발

## 1. 확인된 의도와 해석

기존 DESIGN_SYSTEM.md의 최상위 원칙은 **업체가 비용을 내더라도 감찰 결과를 바꾸지 못한다**는 것이다. 제품의 핵심은 지적→업체의 약속→항목별 재감찰의 변화 기록이다. 귀여운 호랑이는 안내자이며 평가의 근거를 대신하지 않는다.

이 문서는 저장소에서 복원한 설계다. 원본 사업계획서, 별도 기능명세 PDF/HWP/DOCX는 현재 저장소에서 발견되지 않았다. 발견된 제품 문서는 app/DESIGN_SYSTEM.md, 배포 문서는 app/DEPLOY.md이며 README는 Flutter 기본 템플릿이었다. 사용자 마음속의 모든 의도를 확인했다고 단정할 수 없다.

## 2. 역할과 핵심 경험

## 3. 화면군 전체 설계

각 행은 현재 저장소의 화면군에 대한 설계 목표다. ‘이번 구현’ 이외는 설계 또는 기존 구현 확인 단계이며 전체 화면 재구현 완료를 뜻하지 않는다.

| 화면군 | 정보 우선순위와 주 행동 | 반드시 필요한 상태 | 이번 처리 |
|---|---|---|---|
| 스플래시·온보딩·역할 선택 | 가치 설명→소비자/감찰관/업체 목적 선택; 둘러보기 | 초기화 실패, 역할 전환, 인증 복귀 | 기존 흐름 확인·설계 |
| 로그인·회원가입·메일·비밀번호 | 입력 목적→동의→인증; 계속하기 | 중복, 만료, 재전송, 작성값 보존 | 기존 화면 유지 |
| 소비자 홈 | 가치→검색→업종→장단점 감찰→범위가 보이는 랭킹 | 최초 로딩, 섹션 오류, 업종별 없음 | 재구현 |
| 검색 | 이름/설명→업종→결과 수→업체/지역/표본→감찰 기록 | 디바운스, 오래된 응답 폐기, 초기화, 실패 재시도 | 재구현 |
| 전체·지역 랭킹 | 지역·업종·집계 기간→정렬 근거→리뷰 표본 | 데이터 없음, 갱신 지연, 동일 순위 설명 | 홈 연결·기존 상세 유지 |
| 공개 감찰 리포트 | 지적→약속/이력→평균의 표본→장단점 원문 | 공개 API 실패, 지적 로드 실패, 리뷰 0건 | 재구현·공개 API 확장 |
| 리뷰 목록·상세 | 비용 지원 구분→방문 조건→장단점→증거→업체 답변 | 공개/선공개 구분, 신고·수정 이력 | 홈/리포트 연결·기존 상세 유지 |
| 감찰 모집·상세 | 유형·지역·기간·보상·증빙·자격→지원 | 블라인드, 지원 불가, 마감, 배정 | 홈 모집 카드 개선 |
| 감찰 생성·시즌 | 방문/배송/온라인/전화→관찰 항목→예산→게시 | 잘못된 가격, 의뢰 초안, 지급 전 대기 | 기존 흐름 확인·설계 |
| 리뷰 작성·영수증 | 수행 조건→항목별 관찰→사진/영수증→미리보기 | 업로드 실패, 수동 검토, 임시저장, 재접속 | 기존 구현 확인·후속 |
| 교육·시험·튜토리얼 | 수행 책임→학습 진행→평가→인증 상태 | 중단 복귀, 불합격, 재응시, 갱신 | 기존 화면 유지 |
| 역탐지·은밀성·추천 | 조건·목적·권한→참여→명확한 결과 | 민감 정보 최소화, 보상 조건, 오탐 이의 | 기존 화면 유지 |
| 업체 대시보드·분석 | 열린 지적→답변 기한→의뢰 상태→집계 | 실측/예측 분리, 조회 실패 | 후속: 추정 ROI 문구 검토 필요 |
| 선공개·업체 답변 | 원문 보존→사실관계 의견→개선 약속 | 기간 종료, 분쟁, 답변 이력 | 기존 화면 유지·설계 |
| 요금제·결제·해지 | 총액·기간·제공량→결제/해지 확인 | 결제 성공/실패/대기, 중복, 환불 | 별도 상세 설계 아래 참조 |
| 정산·계좌 | 지급 가능/대기/보류 분리→건별 원장→계좌 | 계좌 검증 실패, 송금 보류, 재처리 | 홈의 가짜 0원 제거, 실제 정산 화면 연결 |
| 프로필·내 활동·포트폴리오 | 실제 역할·활동→진행 건→설정 | 비로그인, 기록 없음, 개인정보 | 홈의 고정 루키/미션 0건 제거 |
| 알림·설정·접근성 | 실제 안 읽음→중요도·수신 옵션 | 읽음 실패, 필수 알림 설명, 글자 확대 | 홈의 고정 알림 점 제거·탭 대비 개선 |
| 약관·개인정보·위치·문의 | 운영 주체→항목별 목적/기간→문의 | 실제 회사 정보, 버전, 연결 실패 | 배포 필수값·기존 문서 확인 |

## 4. 데이터와 권한 설계

- 현재 주요 엔티티: users, businesses, missions, reviews, review_findings, notifications, escrows/settlements, subscriptions, 교육·시즌·추천·담합 관련 테이블. 전체 파일 목록은 repository-inventory.md 참조.
- 공개 읽기: 활성 업체, 공개된 리뷰, 공개 가능한 지적/약속/이력. 비공개 배정·연락처·계좌·영수증 원본 개인정보는 별도 접근 제어.
- 감찰 작성: 배정된 감찰관만, 미션 수행 상태를 서버에서 확인. 클라이언트의 user_type은 화면 선호값이며 권한 증명이 아니다.
- 업체 답변: 소유 업체의 공개/선공개 리뷰에 의견을 추가. 별점·지적 원문·개선 확인 상태는 수정 불가.
- 운영 검토: 사유와 근거를 가진 정정/비공개 결정. 영구 삭제보다 변경 이력과 이의 절차 우선.

### 개선 확인의 목표 상태 기계

`open → promised → reinspection_requested → inspected → verified_fixed / still_open / inconclusive`

현재 DB의 open/fixed는 이 상태를 모두 표현하지 못한다. 이번 변경은 ‘다음 리뷰에서 언급 안 됨→fixed’ 자동 처리를 중단한다. 과거 fixed 값을 자동 수정하지 않고 공개 화면에서 재확인 필요로 표시한다.

다음 구현은 `finding_verifications` 테이블을 별도로 두고 finding_id, mission_id, review_id, assigned_reviewer_id, observation, evidence_refs, observed_at, result, checked_by, created_at을 저장한다. 동일 미션/지적에 멱등 키를 둔다. 서버가 해당 업체의 배정된 재감찰인지, 공개된 증빙인지, 긍정 판정과 현재 cons가 충돌하지 않는지 검증한 뒤 트랜잭션으로 상태를 전이한다. 업체 자기 신고는 promised만 변경한다. 증빙 삭제·리뷰 비공개 시 verified를 그대로 유지할지 재검토 상태로 전환하는 규칙도 필요하다.

### 공개 API 계약

- GET /businesses/search: q, category, city. 이번 화면은 이름/설명과 업종만 사용. 최대 50개이며 총 결과 건수로 표현하지 않음.
- GET /rankings/regional: 지역·업종·period(monthly 기본). 홈은 위치를 수집하지 않으므로 ‘내 주변’이라고 표시하지 않음. 서로 다른 지역의 rank를 전국 통합 순위로 재해석하지 않음.
- GET /businesses/:id/trust-analysis: 기존 businessName/category/totalReviews/averageScore 유지, findings/findingsAvailable/timeline/improvement 추가. 지적 저장소 장애는 기록 0건과 구분.
- GET /businesses/:id/reviews: published만. 공개 리포트는 최대 최근 10개를 표시하며 목록 장애도 별도로 표시.
- GET /businesses/:id/report: 업체 소유자용 경쟁력 보고서. 소비자 화면에서 호출하지 않음.

### 증거·후원·점수의 분리

공개됨≠방문 확인됨≠서비스 품질 보증. 방문 사진·GPS·영수증 각각의 확인 상태, 비용 지원 주체/유형/범위, 관찰 결과를 별도 필드로 제공한다. 현재 목록 API에서 없는 인증값을 프론트에서 만들어 넣지 않는다. 5점 평균×20을 ‘신뢰도’라고 읽히게 하지 않으며 이번 공개 리포트는 평균 5점 척도와 표본 수로 표시한다.

## 5. 디자인 시스템

기존 크림 #FDF6E9, 흰 면, 골드 #F2B33D, 먹색 #3D2E1F를 유지한다. 골드 위 글자는 먹색. 붉은색은 지적·오류, 초록색은 근거가 있는 개선 확인에만 사용한다. 좋은 평가 자체는 초록 인증 배지를 붙이지 않는다.

본문은 시스템 한글, 브랜드 제목은 번들 Jua. Jua는 단일 웨이트 w400을 유지한다. 카드와 결과는 자동 높이, 필터는 Wrap, 본문 최대 폭 560, 좌우 12/16px, 섹션 28px. 기존 하단 네비게이션 여백 공통 토큰 사용. 320px 폭과 글자 배율 200%를 검증한다. 캐릭터는 안내에만 사용하고 오류·평가·결제에서는 제외한다.

대표 화면 구성은 design/consumer-discovery-concept.png. 이 이미지는 시안이며 합성 업체·사진·숫자를 포함한다. 실제 앱은 운영 API가 주는 내용만 렌더링한다. 시안의 카드 사진·정렬 선택·확정 개선 배지는 구현 완료 항목이 아니다.

## 6. 결제·정산 상세 설계

1. 결제 전: 구독료, 감찰비, 상품/방문 비용, 수수료, 총액, 자동 갱신일을 명시. 계획 수치와 실제 청구금액을 구분.
2. 승인 요청: 서버 발급 주문 ID와 금액으로 요청. 버튼 중복 실행 방지, 새로고침·복귀 시 주문 상태 재조회.
3. 결과: 결제사 승인 전에는 성공 문구 금지. pending/paid/failed/cancelled를 각각 표시. 동일 승인·웹훅은 멱등 처리.
4. 공개/정산: 기존 상수의 선공개 72시간·자동 해제 7일을 단일 정책 원천으로 사용. 지급 보류는 실제 이유와 이의 경로 표시. 낮은 점수는 보류 사유가 아니어야 함.
5. 해지: 갱신 종료 시각과 남은 제공량·환불 계산을 먼저 표시. 해지 완료 이후 상태를 조회하여 확인. ‘잠시 멈춤’이 해지를 대신 선택되게 하지 않음.
6. 운영 실측 확인: Toss 테스트 주문→승인→취소→중복 웹훅→보류 정산 시나리오를 스테이징에서 검증해야 출시 가능. 이번 작업에서는 실결제·송금을 실행하지 않음.

## 7. 품질 게이트와 지표

- 기능: 공개 탐색 로그인 불필요, 새 검색이 이전 응답에 덮이지 않음, 필터가 서버 요청에 전달, 결과 없음/오류 구분.
- 정보: 표본 없는 점수·금액·등급·알림 배지 금지. 약속과 확인 구분. 원문 장단점을 함께 표시.
- 접근성: 일반 본문 4.5:1, 48 logical px 터치 목표, 큰 글자 스크롤, 아이콘 동작 라벨. 전체 접근성 준수 인증 주장은 별도 감사 이후.
- 검증: flutter analyze, flutter test, node --test; 핵심 화면 PNG 점검. 원격 결제/DB와 로그인된 실제 단말은 별도 테스트.
- 출시 후 지표 제안: 검색→리포트 열람률, 근거 원문 열람률, 결과 0건 비율, 오류율, 지적 답변 시간, 증빙 가능한 개선 확인 비율. 현재 실측값은 없음.

## 8. 남은 결정과 출시 전 작업

- 외부 원본 기획서가 있다면 이 복원 명세와 대조 필요.
- 업종 문자열 체계가 UI와 OFFLINE_CATEGORIES/ECOMMERCE_CATEGORIES 사이에서 불일치: 실제 저장 데이터 분포 확인 후 canonical ID·별칭 마이그레이션 필요.
- 구독 PLAN_DETAILS의 badge feature와 ‘배지는 구매 불가’ 원칙 충돌: 혜택/배지 산정 정책 분리 필요.
- 기존 업체 분석에 고정 예상 매출 +8%/+12% 문구가 존재: 실측 근거가 없는 숫자를 제거하거나 모델·불확실성 공개 필요.
